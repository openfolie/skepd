# RFC-001: Skepd — A General-Purpose Autonomous Agent Runtime

**Status:** Accepted (MVP scope frozen)
**Version:** 0.2.0
**Date:** 19 October 2026
**Target:** Weekend MVP
**Primary language:** TypeScript
**Deployment target:** Single Linux cloud VM
**License:** TBD

## 1. Abstract

Skepd is a general-purpose autonomous agent runtime that accepts a high-level goal, decomposes it into executable tasks, delegates work to specialized agents, verifies results, and continues execution with minimal human supervision.

Unlike a conventional agent framework, Skepd is designed around the operational requirements of long-running autonomy: durable state, dynamic delegation, bounded resource consumption, isolated execution, failure recovery, and independently verified outcomes.

Skepd uses a heterogeneous worker architecture. Strands provides the planning harness, while a deterministic TypeScript scheduler backed by SQLite acts as the authoritative control plane. Workers execute inside isolated workspaces, and OpenTelemetry provides end-to-end observability.

The initial implementation targets one cloud VM and prioritizes correctness, inspectability, and recoverability over distributed scalability.

The central design principle is:

> Agents decide how to accomplish work. The runtime decides what work may execute, what state is authoritative, and whether the result is accepted.

A second principle, added during scope review:

> Skepd must demonstrate autonomous execution under failure, not merely task decomposition. Scope reductions should remove supporting infrastructure before removing the behaviors that make the runtime distinctive.

## 2. Motivation

Current agent frameworks make it relatively straightforward to invoke models, expose tools, and compose multiple agents. However, leaving an agent system unattended introduces problems that are not solved by prompting or agent orchestration alone:

- **Continuity:** Execution must survive process crashes and VM restarts.
- **Coordination:** Agents need to delegate work without losing track of dependencies or creating uncontrolled subagent trees.
- **Verification:** A worker's claim of success must not be confused with actual task completion.
- **Resource control:** Long-running agents must operate within explicit time, token, monetary, and concurrency limits.
- **Isolation:** Agent-generated code and shell commands must not have unrestricted access to the host.
- **Observability:** Operators must be able to reconstruct what happened, identify failures, and understand resource consumption.
- **Heterogeneity:** Different tasks benefit from different agent harnesses, models, tools, and execution environments.

Skepd treats autonomy as a runtime and control problem rather than merely a prompting problem.

## 3. Goals and non-goals

### 3.1 Goals

The MVP MUST:

1. Accept arbitrary natural-language goals with optional constraints, budgets, deadlines, and permissions.
2. Generate structured plans containing tasks, dependencies, acceptance criteria, and worker requirements.
3. Support dynamic delegation and replanning during execution.
4. Support heterogeneous workers through a common execution contract.
5. Persist task state independently of agent conversation sessions.
6. Recover unfinished tasks after worker crashes and application restarts.
7. Execute workers with bounded concurrency and isolated filesystems/processes.
8. Verify task outputs against explicit acceptance criteria.
9. Record task lifecycle events and expose execution traces through OpenTelemetry.
10. Enforce execution limits and terminate or escalate work when limits are reached.

### 3.2 Non-goals

The MVP will NOT attempt to provide:

- A distributed multi-VM scheduler or consensus protocol.
- Kubernetes-based orchestration.
- A general-purpose visual workflow builder.
- Unlimited recursive agent spawning.
- A custom foundation model, inference server, or fine-tuning system.
- A custom agent conversation/session persistence implementation.
- Guaranteed exactly-once execution of arbitrary external side effects.
- Fully autonomous access to unrestricted credentials, networks, or host resources.
- A production multi-tenant security boundary against mutually hostile users.
- Docker isolation (deferred to post-MVP; trusted-user-only with filesystem sandboxing).
- Pi worker integration (deferred; worker adapter interface supports future addition).
- OTLP trace export (console exporter only for MVP).

## 4. Design principles

### 4.1 The control plane is deterministic

Model outputs are proposals, not authoritative state transitions. The scheduler validates every plan, task claim, completion, retry, and cancellation.

### 4.2 State and reasoning are separate

SQLite stores the authoritative state of goals, tasks, dependencies, leases, budgets, and execution events. Agent harnesses own their respective conversation sessions.

### 4.3 Delegation is dynamic but bounded

Agents may propose new tasks at runtime. The scheduler validates and admits those tasks according to dependency, concurrency, budget, and permission constraints.

### 4.4 Completion requires evidence

A worker returning successfully does not automatically mean its task succeeded. Results must satisfy the task's acceptance criteria. Verification is a separate runtime stage.

### 4.5 Heterogeneous execution is a first-class capability

Workers are selected by capabilities and requirements rather than assuming a single agent harness is optimal for every task. The common worker interface allows additional harnesses to be introduced without changing the control plane.

### 4.6 Recovery is designed, not improvised

Every executing task has a lease, every retry is bounded, and every terminal state is recorded. Restart recovery is a core requirement. Recovery restores task state and safely retries interrupted work; it does not resume the exact point of execution inside a model session.

### 4.7 Start with the smallest viable system

Use one process for orchestration, one SQLite database for control state, and a CLI for interaction. Add infrastructure only when a demonstrated limitation requires it.

### 5.1 Strands: planning and supervision

Strands is responsible for:

- Interpreting the user's goal and constraints.
- Producing structured task plans via a required `propose_plan` tool call.
- Identifying dependencies and parallelizable work.
- Recommending worker types and required capabilities.
- Proposing new tasks when execution reveals missing work (replanning).
- Interpreting failures and proposing recovery plans.
- Synthesizing the final result from verified artifacts.

Strands does not directly own durable task state or bypass the scheduler to execute unrestricted operations.

The supervisor may use an agent loop, but each planning or replanning operation is a bounded invocation with explicit context and a limited budget. Planning is one initial attempt plus at most one retry on validation failure. The 60-second timeout bounds the entire attempt.

### 5.2 Worker adapter interface

All harnesses implement a common execution contract.

```typescript
interface WorkerRunner {
  execute(task: Task): Promise<WorkerResult>;
  cancel(taskId: string): Promise<void>;
  health(): Promise<WorkerHealth>;
}

interface WorkerResult {
  summary: string;
  artifacts: ArtifactReference[];
  evidence: EvidenceReference[];
  consumedArtifacts?: { artifactId: string; sha256: string }[];
  attempt: number;  // fencing token, echoed from task
  usage?: {
    inputTokens?: number;
    outputTokens?: number;
    estimatedCost?: number;
  };
}

interface WorkerHealth {
  available: boolean;
  activeTasks: number;
}
```

The interface intentionally excludes direct database mutation by workers. The scheduler handles claims, lease renewal, completion, and retries.

A worker may report partial progress and produce artifacts, but it cannot unilaterally mark a task as accepted. Lease renewal is the scheduler's responsibility via a wrapper that pings the DB on a timer; workers never touch leases.

### 5.3 Worker execution boundaries

Workers may:

- Read and write files within their assigned workspace through a controlled filesystem interface.
- Execute shell commands with the workspace as their working directory.
- Call LLMs (budget reserved by scheduler before invocation, reconciled after).
- Produce artifacts by writing to a designated staging directory (scheduler validates, hashes, and records).

Workers may NOT:

- Access SQLite or directly mutate durable task, event, budget, or artifact records.
- Access other workspaces or the host filesystem outside their workspace.
- Create Git commits, push, or delegate to other workers.
- Access the network (default off, configurable per profile).

All durable state changes flow through the scheduler. The worker adapter wraps tool access and enforces these boundaries.

**Trusted-user-only limitation:** Setting `cwd` to a workspace does not prevent a shell command from accessing files outside it. Environment variables, symlinks, subprocesses, and network access can bypass naïve restrictions. The MVP explicitly retains the trusted-user-only assumption. Real enforcement of filesystem, process, and network boundaries belongs in the later container-isolation phase. Do not claim isolation against malicious code.

## 6. Task model and lifecycle

### 6.1 Goal

A goal represents the user's desired outcome and its execution constraints.

A goal contains:

- Unique identifier.
- Original natural-language specification.
- Success criteria.
- Budget and deadline.
- Allowed capabilities and permissions.
- Current status (`active`, `succeeded`, `failed`, `cancelled`).
- Current plan revision (integer, starts at 0).
- Creation and completion timestamps.

### 6.2 Task

A task is a unit of work that can be independently scheduled, executed, and verified.

A task contains:

- Unique identifier and parent goal identifier.
- Plan revision (integer).
- Planner-local key (unique within goal+revision).
- Description and acceptance criteria (non-empty array).
- Worker type and required capabilities.
- Dependency identifiers (resolved to task IDs; cross-revision deps supported only during replan).
- Status and attempt count.
- Execution deadline and resource budget.
- Lease owner (runtimeInstanceId) and expiration time.
- Workspace and session references.
- Result and evidence references.
- Failure details and verification verdict.
- Metadata (JSON: mockBehavior, side-effect class, etc.).
- Idempotency key (nullable, stable across retries for side-effectful operations).

Tasks form a directed acyclic graph (DAG). The initial implementation rejects cyclic dependencies rather than attempting to resolve them.

### 6.3 Task states

Nine persisted states:

| State | Meaning |
|---|---|
| `pending` | Dependencies not yet met |
| `ready` | Dependencies met, eligible for claiming |
| `executing` | Claimed and running |
| `verifying` | Worker completed, verification in progress |
| `succeeded` | Verified and accepted |
| `failed` | Permanently failed (max attempts exhausted) |
| `cancelled` | Explicitly cancelled |
| `superseded` | Unfinished task from a replaced plan revision (terminal plan-management state) |
| `awaiting_approval` | Requires human approval before execution |

Transitions:

- `pending → ready`: when all dependencies succeeded (transactional, evaluated at scheduling time)
- `ready → executing`: on atomic claim (attempt incremented)
- `executing → verifying`: on worker completion (fencing token validated)
- `verifying → succeeded`: on verification pass
- `verifying → ready`: on verification fail + retry (sets `nextAttemptAt`)
- `verifying → failed`: on verification fail + exhausted
- Any non-terminal → `cancelled`: on cancel (invokes `cancel()`, stops lease renewal, fences late results)
- `ready → awaiting_approval`: when task has `external` side-effect class
- `awaiting_approval → ready`: on explicit approval via CLI
- Unfinished tasks in old revision → `superseded`: on replan

### 6.4 Dynamic delegation

Workers and supervisors may propose additional tasks. The scheduler MUST validate each proposal before admitting it.

Validation includes:

1. Schema and required-field validation (Zod).
2. Dependency existence and cycle detection.
3. Maximum task count and nesting depth.
4. Goal-level budget and deadline constraints.
5. Worker capability and permission checks (workerType validated against registered adapters).
6. Workspace access restrictions.
7. Duplicate localKey detection.
8. Cross-plan dependency resolution (replan only).

Delegation proposals are never executed directly by the proposing agent. They are committed to the task ledger and scheduled like any other task.

Plan acceptance is atomic: validate the entire DAG first, then persist in one transaction. A partially accepted plan is harder to reason about and recover.

### 6.5 Replanning

- Trigger: required task permanently fails, or supervisor explicitly requests replan.
- At most 1 replan per goal in MVP.
- New tasks may depend on already-succeeded tasks from prior revisions (cross-plan deps, referenced by persisted task ID).
- Unfinished tasks in old revision → `superseded`; succeeded tasks remain `succeeded`.
- Goal's `currentPlanRevision` increments.
- Validation retry does not increment active revision.
- If replan exhausted or invalid, goal fails.

## 7. Scheduling and execution

### 7.1 Scheduler responsibilities

The deterministic TypeScript scheduler is the authoritative control plane.

It is responsible for:

- Selecting ready tasks.
- Atomically claiming tasks.
- Managing leases and heartbeats.
- Enforcing concurrency and resource limits.
- Resolving dependencies.
- Recording execution events.
- Applying retry policies.
- Coordinating verification and replanning.
- Cancelling tasks and finalizing goals.
- Recovery on restart.

The MVP uses a bounded worker pool. A default concurrency limit of three is recommended, configurable at runtime.

### 7.2 Claiming tasks

Task claiming MUST be atomic. An explicit transaction:

1. Select eligible `ready` tasks in FIFO order (`createdAt, id`), respecting `nextAttemptAt`, available capacity, and dependencies.
2. Claim selected tasks and increment attempts atomically.
3. Assign lease ownership (runtimeInstanceId) and expiry.
4. Commit before dispatching work.

A worker can claim a task only if:

- The task is ready.
- All dependencies have succeeded.
- The task is not already owned by a valid lease.
- The goal remains eligible for execution.
- Resource and concurrency budgets permit execution.

SQLite transactions protect these transitions.

### 7.3 Lease management

Every executing task has a lease with an expiration timestamp (default 120s, heartbeat 30s).

Workers renew leases while active via scheduler wrapper. If a lease expires, the scheduler considers the task eligible for recovery.

Lease expiration does not prove that the previous worker has stopped. Before retrying, the runtime revokes or fences off the previous execution environment.

On restart, revoke all leases owned by previous runtimeInstances before scheduling replacements.

### 7.4 Retry policy

Retries are bounded and use exponential backoff with jitter.

| Parameter | MVP policy |
|---|---|
| Base delay | 2 seconds |
| Multiplier | 2× |
| Maximum delay | 60 seconds |
| Jitter | Full jitter: uniform random delay from 0 to computed cap |
| Maximum attempts | 3, configurable |
| Formula | `min(60s, 2s × 2^(failedAttempt−1))`, then uniform random in [0, cap] |

Retryable: transient infrastructure errors, rate limits (if budget/deadline permit), worker execution errors (crash/timeout), verification failures.

Terminal (no retry): permission violations, invalid delegation, budget/deadline exhaustion, repeated semantic failure after max attempts.

Verification failures consume an attempt. Reaching the limit transitions the task to `failed`.

### 7.5 Goal supervision

The supervisor wakes when:

- A task completes or fails.
- A dependency becomes satisfied.
- A lease expires.
- A verification verdict requires action.
- New information invalidates the current plan.
- A deadline or budget threshold is reached.

It does not need to continuously invoke a model while waiting for workers.

A goal succeeds only when its declared success criteria are satisfied and its required tasks have been verified. If progress becomes impossible, the supervisor must terminate or escalate instead of reporting false success.

The supervisor's `success` boolean is advisory — the scheduler's deterministic goal-level checks are authoritative. The supervisor cannot override failed deterministic checks.

Goal success evaluation:

- Scheduler determines whether every task in the active plan (current revision) has succeeded.
- Deterministic goal-level acceptance checks must pass.
- Supervisor provides bounded final synthesis (one invocation, 60s timeout, 4096-token cap) and may request additional work via replan.
- If a required task fails permanently, permit at most one replan. If exhausted, fail the goal.
- Cancelling a goal cancels its non-terminal tasks and requests cancellation from running workers. Late results must not revive the goal.

## 8. Persistence and storage

SQLite is the authoritative store for runtime state.

### 8.1 Schema

Five tables: `goals`, `tasks`, `events`, `artifacts`, `model_invocations`.

Key constraints:

- `tasks`: `UNIQUE (goalId, planRevision, localKey)`
- `events`: `UNIQUE (goalId, sequence)` (per-goal monotonic, allocated in same transaction as state change)
- `artifacts`: `UNIQUE (goalId, taskId, path)`
- Foreign keys on `artifacts` and `model_invocations` (including nullable `taskId`)
- `CHECK` constraints for nonnegative attempts, token counts, cost values

JSON fields (acceptance criteria, capabilities, metadata, verification verdict, consumed artifacts) stored as TEXT with Zod validation on read and write.

Domain types do not import Drizzle. The database layer may import domain schemas and enums.

### 8.2 Agent sessions

Agent session persistence remains harness-specific:

- Strands uses its configured session management mechanism.
- SQLite stores session references and task associations.

A conversation transcript is not a substitute for a task ledger. On recovery, the runtime consults the task ledger first, then restores the appropriate agent context.

### 8.3 Artifacts

Artifacts are stored on the local filesystem in a goal-scoped workspace.

- Layout: `./data/artifacts/<goalId>/<taskId>/<artifactName>`
- Hash: SHA-256, computed after writing
- Paths: relative to artifacts root (portable across restarts)
- Record: path (relative), sha256, sizeBytes, mediaType, createdAt, consumedArtifacts
- Artifact registration is scheduler-owned: workers stage candidate outputs; scheduler validates paths, computes hashes, inserts records
- Artifacts are immutable once recorded (hash locked); downstream tasks receive `ArtifactReference` objects with `artifactId`, path, and sha256
- Recompute hash when reading; fail integrity check if mismatch

For the repo-fix demo, expected artifacts: `patch.diff`, regression test file, `test-run.log` (command + exit code + bounded output), `report.md`.

### 8.4 Workspaces

- Goal input: `goal.context.repoPath`, validated to exist and be a git repo at goal creation
- Execution workspace: worktree for the goal's active plan revision, based on recorded base commit
- Original repository never mutated by workers
- Worker produces `patch.diff` via `git diff` as an artifact
- Verifier applies patch to fresh worktree at base commit, runs configured test command independently
- Multi-task plans: serialize mutations or require explicit patch integration; single coding task for first demo
- Test command: must be safely determined from repo scripts or explicitly configured; never guess
- Worktrees retained for inspection (cleanup deferred to post-MVP)

### 8.5 Model invocation ledger

- Pre-invocation: atomically check goal status, deadline, call budget, cost budget → insert `reserved` invocation with unique ID and estimated cost → reserve budget capacity → increment counters
- Post-invocation: reconcile against actual usage where available
- Crash handling: invocation remains `reserved` or `uncertain`; must not be mistaken for success or charged as zero
- `uncertain` status: request may have reached provider but outcome not recorded
- Conservative accounting: cancelled/aborted calls retain reservation until reconciled
- Reconciliation via CLI: `skepd goal reconcile <invocationId> --outcome confirmed|not-applied|unresolved` with evidence

## 9. Isolation and permissions

Workers execute in dedicated workspaces with explicit resource and capability limits.

The runtime MUST:

- Avoid privileged containers (deferred to post-MVP).
- Mount only the required workspace paths.
- Apply CPU, memory, process, and execution-time limits.
- Restrict credentials to the minimum required for a task.
- Make network access configurable by worker profile (default off for coding workers).
- Keep control-plane database files inaccessible to worker processes.
- Validate artifact paths to prevent traversal outside permitted directories.

Host execution is reserved for the trusted scheduler and runtime components.

The initial deployment assumes one trusted operator. Filesystem sandboxing with strict path validation is used, but this does not safely isolate arbitrary untrusted execution. Docker isolation is a documented follow-up.

### 9.1 Human approval

Tasks involving consequential external side effects, privileged access, or permissions beyond the goal's granted scope require explicit approval.

Implemented as `awaiting_approval` state with CLI commands `approve` and `reject`. A rejected task must not silently return to the ready queue.

Autonomy does not imply unrestricted authorization.

## 10. Verification and result acceptance

Verification is a separate runtime stage.

Each task defines acceptance criteria before execution. The verifier evaluates the produced artifacts and evidence against those criteria.

Interface:

```typescript
interface Verifier {
  verify(task: Task, artifacts: Artifact[]): Promise<VerificationResult>;
}

interface VerificationResult {
  passed: boolean;
  reason: string;
  evidence: { check: string; passed: boolean; detail?: string }[];
}
```

The scheduler invokes verification inline (synchronously, same process, task stays in `verifying`) immediately after worker completion. It does not consume a worker slot.

Persist verification result and evidence before applying terminal/retry transition, in the same transaction.

Verify actual evidence, not worker assertions. For the demo: patch file exists and non-empty, regression test file exists and contains a test, test command exit code 0 (independently run by verifier in fresh worktree), report file exists referencing artifact paths. Record command, exit code, and bounded stdout/stderr in `test-run.log`.

Verification failures enter the same retry policy, with failed checks retained for debugging and replanning.

The final goal result contains:

- A concise summary.
- Links or paths to verified artifacts.
- Verification outcomes.
- Known limitations or unmet criteria.
- Resource usage and execution history.

Skepd must not silently convert an unsuccessful or partially completed goal into success.

## 11. Observability

OpenTelemetry is the standard instrumentation layer.

Console exporter for MVP (`ConsoleSpanExporter`). OTLP export deferred.

Trace context propagates across: goal → task → worker invocation → model call → tool invocation → verification. Trace IDs stored in `events.traceId` (nullable).

Span attributes: `skepd.goal.id`, `skepd.task.id`, `skepd.task.attempt`, `skepd.worker.type`, `skepd.tool.name`.

Strands native instrumentation used where available; manual spans for scheduler and verification. Verify context survives async boundaries and SDK-managed tool loops.

Sensitive prompts, credentials, and raw tool output must not be emitted to telemetry by default. Explicit redaction required.

## 12. Technology choices

| Layer | MVP choice | Rationale |
|---|---|---|
| Language | TypeScript | One language across scheduler, API, and worker adapters |
| Runtime | Node.js | SDK compatibility |
| Planning | Strands TypeScript SDK | Planning, model abstraction, tools, instrumentation |
| Coding execution | Strands worker (configured) | Reuse Strands integration; Pi deferred |
| Control plane | SQLite (Drizzle + better-sqlite3) | Durable, inspectable single-host state; type-safe ORM |
| Validation | Zod | Validate plans, task definitions, worker results, config |
| Isolation | Filesystem sandboxing (trusted user) | Docker deferred to post-MVP |
| Observability | OpenTelemetry (console) | Correlated runtime and agent traces |
| Interface | CLI (commander.js) | Minimal surface area for first milestone |
| Testing | Vitest | Fast, TypeScript-native |

### 12.1 Why not use Celld initially?

Celld is a potential future runtime foundation. The MVP has one VM and one local control database. Introducing Celld immediately would add another runtime abstraction before the project has established which durability and scheduling semantics it actually needs. SQLite and explicit TypeScript state transitions first. Celld can be evaluated later against demonstrated gaps.

### 12.2 Why not use Pi initially?

Pi is a strong execution harness for coding workflows, but a persistent agent session does not automatically provide a complete autonomous task scheduler. Skepd requires explicit dependency management, task leases, retry policies, budget enforcement, verification, and recovery semantics. These belong in the runtime. Pi integration is deferred; the worker adapter interface supports future addition without changing the control plane.

### 12.3 Why not use Strands alone?

Strands could handle the initial workload by itself, but Skepd deliberately supports heterogeneous workers. The common worker interface allows additional harnesses (Pi, etc.) to be introduced without changing the control plane.

## 13. Failure handling and consistency

Skepd provides recoverable task execution, not universal exactly-once semantics.

| Failure | Required behavior |
|---|---|
| Worker process crashes | Detect failure or lease expiration; recover or retry |
| Application restarts | Reload unfinished goals and resume scheduling; revoke stale leases |
| Duplicate completion event | Make state transitions idempotent (fencing token) |
| Repeated transient failure | Apply bounded retry and backoff |
| Verification failure | Retry or replan within configured limits |
| Budget exhaustion | Stop new work and enforce termination policy |
| Dependency failure | Block dependent work or replan |
| Partial external side effect | Reconcile where possible; do not assume automatic rollback |
| Invalid delegation proposal | Reject and record the reason |
| Uncertain model call | Conservative accounting; reconciliation required |
| Cancelled task late result | Fenced out by attempt + lease owner check |

Exactly-once execution of arbitrary external actions is not guaranteed. Where external actions support idempotency keys, Skepd uses them (stable `operationId` across retries). Otherwise, uncertain outcomes must be reconciled before blindly retrying potentially consequential operations.

## 14. Configuration

Config file: `skepd.config.yaml` at project root (or `--config` flag). Parsed with `yaml`, validated by Zod at startup. Invalid config fails fast with clear path and reason.

```yaml
runtime:
  max_concurrent_tasks: 3
  max_tasks_per_goal: 40
  max_delegation_depth: 4
  lease_seconds: 120
  heartbeat_seconds: 30
  max_attempts: 3

limits:
  max_goal_duration_seconds: 3600
  max_model_calls: 150
  max_estimated_cost_usd: 5
  max_cost_per_task_usd: 1

workers:
  strands:
    enabled: true
    containerized: false
    network: false

observability:
  opentelemetry: true
  exporter: console
  emit_sensitive: false

storage:
  database: ./data/skepd.db
  artifacts: ./data/artifacts
  sessions: ./data/sessions
```

Configurable: concurrency, task/delegation limits, lease/heartbeat, max attempts, goal duration, model calls, estimated cost, per-task cost, worker profiles (enabled, containerized, network), observability (exporter, emitSensitive).

Hardcoded: task state machine, event catalogue, side-effect classes, verification rules, adapter registration.

Safeguards:

- Operator caps: goal-level overrides cannot exceed global limits.
- Configuration invariants: positive concurrency/attempts/lease duration; heartbeat < lease; no negative budgets.
- No ambiguous unlimited values: `null` = explicitly unlimited; never `0` or missing.
- Credentials via environment variables, never in YAML.
- `containerized: true` must not imply Docker isolation is implemented; reject or flag if deferred.

## 15. Implementation plan

### Phase 1 — Durable execution core

- Establish TypeScript project and configuration.
- Implement SQLite migrations and repositories (Drizzle).
- Implement goals, tasks, dependencies, and state transitions.
- Implement atomic claiming, leases, heartbeats, and recovery.
- Implement mock worker to test scheduler behavior without model calls.

**Exit criterion:** Tasks execute, recover after process restart, and cannot be claimed concurrently by multiple workers.

### Phase 2 — Agent integration

- Integrate Strands TypeScript SDK.
- Implement structured planning and dynamic delegation.
- Implement worker profiles and common execution contract.
- Persist harness session references.

**Exit criterion:** A goal can produce a task graph and dispatch work to a worker.

### Phase 3 — Isolation and verification

- Implement controlled workspace and artifact handling.
- Add deterministic verification hooks.
- Add bounded retries, deadlines, cancellation, and resource enforcement.
- Implement approval state and CLI.

**Exit criterion:** Workers cannot access control database directly, and unverified outputs cannot be reported as accepted.

### Phase 4 — Observability and unattended operation

- Add OpenTelemetry instrumentation (console exporter).
- Implement supervisor wake-up and replanning.
- Add goal status and event inspection commands (terminal timeline).
- Run fault-injection tests (killed workers, application restarts).

**Exit criterion:** System completes multi-step goal unattended, recovers from injected failures, stays within configured limits, produces inspectable evidence of success.

## 16. Acceptance criteria for the weekend MVP

The MVP is considered functional when it passes all of the following:

1. Accept a natural-language goal with a deadline and budget.
2. Generate a validated DAG containing dependent and parallel tasks.
3. Execute tasks using a real worker and mock worker.
4. Dynamically add tasks after execution begins.
5. Execute no more than the configured concurrency limit.
6. Reject invalid or cyclic task graphs.
7. Recover unfinished tasks after killing a worker process.
8. Resume unfinished goals after restarting the application.
9. Reject a task whose output fails verification.
10. Stop scheduling work when goal budget or deadline is exhausted.
11. Produce a final report containing verified artifacts and failed or incomplete work.
12. Correlate goal, task, and worker activity in execution events and traces.

Additional acceptance tests from scope review:

13. A stale result cannot alter task state or artifacts after a newer attempt has been claimed.
14. Restart recovery revokes pre-restart execution authority before redispatch.
15. Retry eligibility respects global attempt limit, budget, deadline, and `nextAttemptAt`.
16. Verification evidence is persisted and independently derived from execution artifacts.
17. Concurrent claims never exceed configured limit.
18. Scheduler's fallback timer handles expired leases and due retries without state-change events.

The first end-to-end demonstration:

"Inspect this repository, identify and fix a reproducible bug, add a regression test, run the relevant test suite, and produce a report of the change."

This exercises planning, repository inspection, delegation, coding, verification, artifact production, and final synthesis without requiring complicated external integration.

## 17. CLI commands

```
skepd goal create "<spec>" --repo <path> [--test-cmd <cmd>] [--budget <usd>] [--deadline <sec>]
skepd goal status <goalId>
skepd goal events <goalId> [--tail N]
skepd goal cancel <goalId>
skepd goal approve <taskId>
skepd goal reject <taskId>
skepd goal reconcile <invocationId> --outcome confirmed|not-applied|unresolved [--evidence <ref>]
```

Output: plain stdout with compact tables and event timeline. `--json` flag for machine-readable output. No TUI for MVP.

`goal status`: task table (id, status, attempt, worker, verification) + budget summary + goal state.

`goal events`: terminal timeline (compact, icon-prefixed, chronological by sequence number).

## 18. Tool registry

Central `ToolRegistry` singleton. Each tool declares:

```typescript
interface ToolDefinition {
  name: string;
  description: string;
  idempotent: boolean;
  hasExternalSideEffects: boolean;
  supportsProviderIdempotencyKey: boolean;
  sideEffectClass: 'none' | 'local_write' | 'git_write' | 'network' | 'external';
  execute(ctx: ToolContext, args: unknown): Promise<ToolResult>;
}
```

Workers receive filtered subsets based on profile. Scheduler enforces permissions, budget, approval, and operation tracking at execution time.

Demo tools: `read_file`, `write_file`, `run_command`, `git_diff`, `git_status`, `git_branch`. Network and `git_push` excluded by default.

`run_command` requires runtime enforcement of allowed commands and execution policy — metadata alone cannot make arbitrary shell execution safe.

## 19. Side-effect classification

| Side-effect class | MVP policy |
|---|---|
| `none` | Read-only; retryable |
| `local_write` | Workspace writes; retryable under workspace recovery rules |
| `git_write` | Local branch/patch operations; retryable after workspace reset and fresh verification |
| `network` | Allowed only when explicitly granted; retry depends on operation semantics |
| `external` | Approval required for consequential external mutations |

The planner cannot grant itself additional permissions. Validate every proposed task against the goal's granted capabilities, then enforce those permissions again when tools execute.

`awaiting_approval`: distinct persisted state, excluded from scheduling until explicit approval transitions it to `ready`. Implement state and CLI approval path; no full approvals framework.

Network read-only HTTP can be permitted by policy. Network mutations classified by actual operation and idempotency guarantees.

## 20. Idempotency

Two identifiers:

- `operationId`: stable across retries of the same logical side effect.
- `attempt`: changes on each task claim, fences stale worker results.

Scheduler generates `operationId` (UUID) when a side-effectful operation is first registered. Reused on retry. Provider idempotency key derived from `operationId` where supported.

Tool metadata declares: `idempotent` (operation is repeat-safe), `hasExternalSideEffects` (performs external mutation), `supportsProviderIdempotencyKey` (provider accepts idempotency key). Three independent properties.

Non-idempotent operations:

- Read-only or repeat-safe commands: retry.
- Local Git operations: recreate/reset worktree, regenerate patch, independently verify.
- External mutations with unknown outcomes: block automatic retry, require reconciliation or human review.

## 21. Recovery from uncertain outcomes

1. On recovery, mark unresolved model invocations as `uncertain` when request may have reached provider but outcome not recorded.
2. Retain cost reservation until reconciliation or defined conservative accounting decision.
3. Retry interrupted local work only after resetting/recreating workspace and confirming operation is repeat-safe.
4. Block automatic retries for uncertain, non-idempotent external operations. Require `skepd reconcile` to resolve.
5. Record reconciliation outcomes in append-only `events` table.

`uncertain` added to `model_invocations.status`. Optional `reconciliationStatus` JSON field for model-call accounting uncertainty (distinct from external side-effect reconciliation).

Human reconciliation must provide evidence. CLI supports explicit outcomes: confirmed applied, confirmed not applied, or unresolved. Audit event records decision + evidence + actor + timestamp.

A task may be interrupted while a side effect has unknown outcome. Returning task to `ready` is safe only when outstanding operations are known to be retry-safe.

## 22. Risks and mitigations

**Agent drift:** Long-running agents can lose focus or repeat unsuccessful approaches.
*Mitigation:* Persist task specifications and acceptance criteria outside conversation history, bound attempts, replan after repeated failures.

**Uncontrolled delegation:** Agents may create excessive tasks or duplicate work.
*Mitigation:* Central admission control, task caps, DAG validation, budget enforcement.

**Duplicate side effects:** Recovery may cause an operation to execute twice.
*Mitigation:* Idempotency keys (operationId), reconciliation, explicit approval for consequential operations.

**False completion:** A worker may report success despite incomplete work.
*Mitigation:* Independent verification and evidence-backed acceptance. Scheduler verifies artifacts by hash and independent test execution.

**Framework coupling:** Different agent harnesses expose different tools and lifecycle behavior.
*Mitigation:* Keep harness-specific logic inside worker adapters and standardize only the execution contract.

**Observability overhead:** Tracing every event can increase storage use and expose sensitive information.
*Mitigation:* Structured, bounded instrumentation with sensitive data excluded by default.

**Security limitations:** Containers alone do not guarantee strong isolation against hostile workloads.
*Mitigation:* Single-operator assumptions for MVP, restricted mounts and credentials, resource limits, explicit future security review.

## 24. Open questions (resolved)

All open questions from RFC v0.1.0 have been resolved through the grilling process:

- Planning and replanning use the same model (Strands), with bounded invocations.
- Worker capabilities: read_file, write_file, run_command, git_diff, git_status, git_branch by default.
- Initial verifier: hybrid (deterministic rule engine for MVP, model-based judging deferred).
- Checkpoint format: SQLite state + artifact hashes; no separate checkpoint format needed.
- Automatic replanning triggered by permanent task failure or supervisor request; max 1 replan.
- Celld: deferred until demonstrated need.

## 25. Conclusion

Skepd is a single-host autonomous agent runtime built around heterogeneous execution, durable task state, bounded delegation, and verifiable outcomes.

Its architecture separates three responsibilities:

- **Strands** handles planning, reasoning, and supervision.
- **The deterministic TypeScript runtime** owns task state, scheduling, permissions, recovery, and acceptance.
- **SQLite** provides the control plane, **workspaces** provide execution isolation, and **OpenTelemetry** provides observability.

The project's first objective is to demonstrate that a small collection of agents can accept a meaningful goal, work unattended, survive failures, stay within limits, and produce a verified result.

That is the foundation on which a more capable autonomous runtime can be built.
